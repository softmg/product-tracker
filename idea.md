# Идея: Product Tracker

## Подходящий skill

Для описания идеи использован подход `product-discovery` из skills.sh:
https://skills.sh/majiayu000/claude-arsenal/product-discovery

Причина выбора: skill требует начинать с проблемы и ожидаемого исхода, фиксировать проверяемые предположения и заранее назначать роли discovery. Это ближе к форме создания гипотезы в Product Tracker, чем PRD-first подход.

## Как заполнить форму идеи на примере этого проекта

Открыть `/hypotheses/new` и заполнить поля так:

| Поле | Значение |
| --- | --- |
| Название | `Product Tracker: единая воронка продуктовых гипотез SMG` |
| Проблема / боль клиента | `Идеи, скоринг, deep dive, эксперименты и решения продуктового комитета ведутся в разных местах. Из-за этого команда теряет статус, SLA, ответственных, артефакты исследований и историю решений.` |
| Формулировка решения | `Мы верим, что если SMG внедрит единый сервис для управления продуктовыми гипотезами от идеи до Go/No-Go/Iterate, то команды быстрее доведут идеи до проверяемого решения, а продуктовый комитет получит прозрачный паспорт гипотезы.` |
| Ключевые предположения | `Инициаторы готовы описывать идеи структурно. PD-менеджеры будут вести статус и SLA. Аналитики, tech lead и bizdev смогут работать в одной карточке. Комитету достаточно паспорта гипотезы для решения.` |
| Целевая аудитория | `Внутренние продуктовые команды SMG: инициаторы, PD-менеджеры, аналитики, tech lead, bizdev, администраторы процесса и продуктовый комитет.` |
| Приоритет | `Высокий`, если цель ближайшего цикла - навести порядок в discovery-воронке; иначе `Средний`. |
| Команда | `Product` или команда, ответственная за внутренние продуктовые процессы. |
| Владелец | PD-менеджер, который отвечает за прохождение идеи по воронке. |

## Какой outcome проверяем

Идея должна доказать, что единая карточка гипотезы снижает ручную координацию и делает статус discovery видимым для всех участников.

Сигналы успеха:

| Сигнал | Как понять, что идея работает |
| --- | --- |
| Полнота входа | Большинство новых идей создаётся с заполненными проблемой, решением, предположениями и аудиторией. |
| Скорость первичной обработки | PD-менеджер быстрее переводит идеи из `Идея` в `Скоринг`. |
| Управляемость SLA | Команды видят просрочки и ответственных без ручных сверок. |
| Качество решения ПК | Комитет получает историю, scoring, deep dive и эксперименты в одном паспорте. |

## Кто может создать идею

По текущей frontend-модели прав `hypothesis:create` есть у ролей:

| Роль | Может создать идею | Что делает |
| --- | --- | --- |
| `initiator` | Да | Заводит исходную идею и описывает проблему, решение, аудиторию, предположения. |
| `pd_manager` | Да | Может завести идею сам или от имени продуктового процесса, затем контролирует движение по воронке. |
| `admin` | Да | Может создать идею для проверки процесса или администрирования, но не является бизнес-владельцем discovery. |
| `analyst` | Нет | Подключается на scoring/deep dive, помогает с данными и исследованиями. |
| `tech_lead` | Нет | Оценивает техническую реализуемость, риски и ресурсы. |
| `bizdev` | Нет | Проверяет коммерческий потенциал, партнёрства, unit economics. |
| `committee` | Нет | Не заводит идеи, принимает Go/No-Go/Iterate на этапе продуктового комитета. |

Важно для QA: UI сейчас ограничивает создание ролями `admin`, `initiator`, `pd_manager`. Backend `StoreHypothesisRequest` разрешает сам request всем авторизованным пользователям, поэтому production-policy нужно синхронизировать с тем же набором ролей.

## Кто контролирует дальше

Основной контролёр после создания - `pd_manager`. Он проверяет полноту карточки, назначает владельцев, следит за SLA и переводит идею по статусам.

Контроль по этапам:

| Этап | Контролирует | Участвуют |
| --- | --- | --- |
| Идея → Скоринг | `initiator`, `pd_manager`, `admin` | Инициатор уточняет входные данные, PD-менеджер принимает в работу. |
| Скоринг → Deep Dive | `pd_manager`, `analyst`, `admin` | Аналитик проверяет данные и scoring, PD-менеджер принимает решение о глубокой проверке. |
| Deep Dive → Эксперимент | `pd_manager`, `admin` | Аналитик, tech lead и bizdev закрывают свои блоки анализа. |
| Эксперимент → Питч | `pd_manager`, `admin` | Команда фиксирует результаты эксперимента и готовит паспорт. |
| Питч → Done/Archive | `admin` по текущим transition seeders | `committee` принимает бизнес-решение Go/No-Go/Iterate, admin фиксирует финальный системный статус. |

Для этой идеи владельцем контроля должен быть `pd_manager`, потому что Product Tracker - это не только разработка интерфейса, а управление discovery-процессом от входа идеи до решения комитета.
